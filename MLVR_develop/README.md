# MLVR_develop —— RMC 机器学习减方差开发工作区

> 目的：每一个开发任务 / 缺陷修复 / 算法实验都留下**可追溯、人可复核**的处理档案。
> 原则：**证据先行、人拍板、改动留痕**。Agent 负责定位与实施，最终决定权在人。

## 任务模式：先选参与深度，再走同一套五步关口

所有任务仍必须走五步工作流；任务模式只规定人需要理解什么、档案需要增加什么，**不降低** RMC 修改、基准冻结、提交/push 等硬规则。

| 模式 | 适用任务 | 人的参与重点 | 额外必填产物 |
|---|---|---|---|
| A — 受约束自动化 | 已批准的重复验证、资料整理、机械性汇总 | 确认范围、输入和最终产物 | 无；保留五步记录与真实输出 |
| B — 工程协作（默认） | 常规工具、接口、已知缺陷修复、原型实现 | 方案、接口/兼容性、验证覆盖 | 变更卡；需要时记录回滚方案 |
| C — 深度物理研究与学习 | 伴随、核数据、WW、互易性、统计、训练数据和会改变物理结论/边界的任务 | 问题定式、因果链、结果解释和结论边界 | 内嵌在档案三处：**物理解释**（第 1 节）、**人类理解确认**（第 3 节）、**结果解释**（第 4 节） |

**选择规则**：未特别说明时使用模式 B。用户可直接说“用模式 A/B/C”；出现新的物理结论、改变适用范围、未知统计异常、基准/模型更新或跨越既有冻结边界时，Agent 必须建议升级到模式 C。任务可升级，不得在未记录理由的情况下从 C 降级到 A/B。

**证据等级（E0–E4，可选）与治理标签**：物理/审查结论建议标注；工程、文档、治理任务可省略。证据等级只说明证据强度；冻结、可复现、边界和原始证据归档另列为治理标签，不能单独提升证据等级。

| 等级 | 含义 |
|---|---|
| E0 | 假设、计划或未验证主张 |
| E1 | 静态代码/文档证据 |
| E2 | 最小动态路径：构建、运行或 smoke 证据 |
| E3 | 针对性、预定义的数值/统计验证证据 |
| E4 | 独立复现或多维交叉验证证据 |

| 治理标签 | 含义 |
|---|---|
| 已冻结 / 未冻结 | 计划、配置或结论是否已由人决策冻结 |
| 可复现 / 部分可复现 | 运行所需输入、环境和步骤的可复现程度 |
| 边界已定义 / 未完全定义 | 结论适用范围是否明确记录 |
| 原始证据已归档 / 未完整归档 | 支撑结论的原始输出是否可追溯 |

## 任务类型

| 类型 | 典型场景 | 第 ② 步重点 |
|---|---|---|
| 新功能 | 新增 RMC 输入卡 / 新模型变体 / 新接口 | 架构影响面、接口设计 |
| 算法实验 | 新 loss / 先验 / 训练策略对比 | 实验设置、基准对比、可复现性 |
| 缺陷修复 | WW 实现 bug、收敛异常、内存问题 | 根因证据链、影响面 |
| 性能优化 | 训练/推理/MC 循环加速 | 基线 profile、瓶颈证据 |
| 文档 | 知识库/接口规格更新 | 事实核对 |

## 目录约定

```
MLVR_develop/
  README.md                        本文件（工作流规范）
  INDEX.md                         ★ 任务总台账，一行一个任务，先看这里
  new_task.sh                      建档脚本
  _template/README.md              单任务记录模板
  YYYY-MM/                         ★ 按月份归档（new_task.sh 自动创建）
    YYYYMMDD_NN_<任务短名>/        ★ 一个任务一个文件夹（NN=当天工作顺序，01 起两位）
      README.md                    ★ 全过程记录（5 节：目标与范围 / 做法与证据 / 决策 / 结论与边界 / 过程）
      logs/                        原始报错、训练日志、失败产物（原样保存，不加工）
      changes.diff                 本次代码改动快照（有代码改动才有）
```

> ⚠️ 原始聊天转储**不要**存进仓库（可能含口令/token）；留纪要即可，且必须脱敏。

命名示例（`NN` 为当天序号，由 `new_task.sh` 自动生成；任务放入对应月份目录）：
- `2026-08/20260824_01_workflow-baseline/`（8 月 24 日第 1 个任务）
- `2026-08/20260825_04_f02-w7-neutron-only-adjoint-init-fix/`（8 月 25 日第 4 个任务）

同一天多个任务靠 `NN` 序号区分先后；短名要能"看名字就知道是什么事"。

## 五步工作流

```
 选 A/B/C 模式 ─► ① 立项 ─► ② 设计/定位 ─► ⛔ 停 · 你拍板 ─► ④ 实施+自验 ─► ⑤ 归档
 (Agent)      (Agent)            (人)              (Agent)        (Agent+人)
```

| 步 | 谁 | 做什么 | 产出 |
|---|---|---|---|
| ① 立项 | Agent | 确定 A/B/C 模式 → 建档，原始材料**原样**存进 `logs/`，写清目标/范围/完成标准 | 档案第 1 节 |
| ② 设计 | Agent | 读代码/查知识库 → 给出证据、方案与代价；**不确定就直接问人** | 档案第 2 节上半 |
| ⛔ 停 | **你** | 拍板或改需求；Agent 负责把选项和代价讲清（必要时用问答推进） | 档案第 3 节 |
| ④ 实施 | Agent | 改代码 → `changes.diff` → 跑验证（物理从严、工程从简）→ 贴真实输出 | 档案第 2 节下半 |
| ⑤ 归档 | Agent→你 | 更新 INDEX、按需同步知识库；**你决定是否 commit/push** | 档案第 4、5 节 |

**硬规则**：第 ③ 步必须停下等你。Agent 不得在未拍板前改 `../RMC` 下的任何文件。
（只读排查、写 `MLVR_develop/` 与 `MLVR_Knowledge/` 下的记录不受此限。
`../AIMC_WWiteration/` 原型改动较宽松，但建议同样留痕。）

## 补充约定（比"只写文档"更有效，成本很低）

### 1. 改动必须落成 `changes.diff`
实施后执行：
```bash
git -C ../RMC diff > <任务文件夹>/changes.diff
# 改原型则：
git -C ../AIMC_WWiteration diff > <任务文件夹>/changes.diff
```
这样你不用翻代码仓库就能一眼看全本次改了什么。这是"人要知道代码怎么迭代"的关键抓手。

### 2. 一任务 = 一分支 = 一提交，消息里带文件夹名
```bash
git -C ../RMC checkout -b feat/mlvr-<任务短名>
git -C ../RMC commit -m "feat(mlvr): <一句话> (MLVR_develop/2026-08/20260824_01_xxx)"
```
好处：**双向可查**——从 git 历史能找到档案，从档案能找到提交。
不想开分支时至少保证 commit message 里带文件夹名。

### 3. 与知识库联动
- 实现/修复的是知识库 [06_已知问题与改进建议](../MLVR_Knowledge/06_已知问题与改进建议.md)
  里的条目 → 在该条目下标注 `已修复 → MLVR_develop/<任务文件夹>`。
- 发现**新问题/新方法结论** → 归档时补写进 06 或对应专题文档，让知识库始终是最新全景。
- 改动影响架构/接口/方法 → 同步更新知识库 01~05 对应章节的"变更记录"。

### 4. 实验可复现性（涉及训练/数值实验时）

| # | 必记录项 | 位置 |
|---|---|---|
| 1 | 随机种子、`src/config.py` dataclass 配置快照 | 档案 README"实验设置" |
| 2 | 依赖版本：CUDA / PyTorch / numpy / numba / 编译器 | 档案 README"实验设置" |
| 3 | 运行命令（含 `--quick` 等 CLI 参数）、输入卡 | 档案 README 第 6 节 |
| 4 | 基准对比基线（模拟 MC / 指数 WW / 原型同变体） | 档案 README"结论" |
| 5 | 模型/权重产物（`.h5`）与生成它的配置一一对应 | 任务文件夹或知识库登记 |

### 5. 变更卡与模式 C 的人工理解关口

模式 B/C 的决策节必须包含一张**变更卡**：问题与风险、拟改动对象、不改什么、预期因果链、验证与回滚方式。模式 C 还应在下列关口停下让人确认理解，而不是只批准 Agent 操作：

1. **问题定式**：物理量、正确关系、成功/失败可观测量是什么；
2. **因果链**：从物理假设到代码位置、再到可观测偏差的路径是否成立；
3. **验伪设计**：什么结果会推翻当前根因或结论；
4. **结果解释**：验证通过/失败分别代表什么，不外推到哪些机制、平台或统计范围。

模式 C 的“人类理解确认”必须由人直接填写，或由 Agent 转述后获得人明确确认；Agent 不得把自己的推断伪装成人的理解。

### 5b. 档案最小要素与异构来源

档案允许异构（例如其他 Agent 按其工作流产出的报告），但**任何**档案都必须回答三件事：

| 要素 | 含义 | 常见章节名 |
|---|---|---|
| 结论 | 本任务判定/实现了什么 | 结论、Classification、Verdict |
| 证据 | 支撑结论的真实输出位置 | 验证/实验记录、变更与证据、Verification |
| 边界 | 结论不外推到哪些范围 | 范围外、限制、Restrictions、Limitations |

不满足三要素的档案必须先转写成模板；满足的可以保留原结构，但需在基本信息区标注来源与格式（例如“外部 Agent 执行，登记型档案”）。`bash tools/check-archives.sh` 会按三要素检查模式 C 档案。

### 5c. 验证强度：分场景，不做无限验证

| 场景 | 要求 |
|---|---|
| 物理结论 / 要写进论文或用于关键决策 | 需要能支撑结论的真实证据：可复现命令 + 输出 + 必要的统计量 |
| 工程 / 文档 / 治理 | 跑通代表性用例即可；不做 formal 全矩阵、多重假设检验、独立审计 |

默认**信任前人实现**：审查以抽查关键路径为主，不追求穷尽。说不清的结论就如实写“未验证”，而不是堆验证。

### 5d. 提问约定

- **随时问、宁多勿少**：需求不清、方案取舍、物理判断、范围边界，直接问人，不要替人假设；
- 每次提问不超过 3 个、尽量给可选项；
- 不用长文档代替对话——档案是给人**复核**的，不是给人**阅读**的。

### 6. 归档检查清单（⑤ 归档时逐项自检，避免人提醒才补）

| # | 检查项 | 位置 |
|---|---|---|
| 1 | 档案 5 节完整，状态与台账一致 | 档案 `README.md` / `INDEX.md` |
| 2 | 结论、证据、边界三要素齐（异极文档也适用） | 档案第 2、4 节 |
| 3 | 验证输出真实，未覆盖项如实写明 | 档案第 2、4 节 |
| 4 | `changes.diff` 最新（有代码改动才有）；实验类含种子/配置/命令 | 档案目录 |
| 5 | 知识库 / 物理导读按需同步（结论或边界变化才必须） | `MLVR_Knowledge/` |
| 6 | `bash tools/check-archives.sh` 无“需处理”项 | 工作区根目录 |

### 7. 归档体积规范

- `logs/` 不存可再生成的产物：构建目录、二进制、RMC 运行产物、训练中间 checkpoint 等，
  需要时写重现命令而不是存文件；
- 单文件 >10MB 须先与用户确认是否必要；
- 大量同类过程文件优先**整合成脚本 + manifest**，而不是逐个上传。

清理这些可再生成目录时，先预览再显式执行：

```bash
./clean_generated.sh
./clean_generated.sh --apply
```

脚本只处理任务顶层 `runs/`、`cases/` 和 `__pycache__/`，不会删除 `logs/`、资产、README 或改动快照。

## 状态词表（INDEX.md 里只用这几个）

| 状态 | 含义 |
|---|---|
| `待设计` | 已立项，尚未完成设计/定位 |
| `待决策` | 设计/根因清楚，方案已给，**等你拍板** |
| `实施中` | 已拍板，正在改 |
| `待验证` | 改完了，等本地实验 / CI / 回归结果 |
| `已完成` | 验证通过并已归档（是否 push 由你决定） |
| `已关闭` | 决定不做（须在 README 写明理由） |
