# MLVR_develop —— RMC 机器学习减方差开发工作区

> 目的：每一个开发任务 / 缺陷修复 / 算法实验都留下**可追溯、人可复核**的处理档案。
> 原则：**证据先行、人拍板、改动留痕**。Agent 负责定位与实施，最终决定权在人。

## 任务类型

| 类型 | 典型场景 | 第 ② 步重点 |
|---|---|---|
| 新功能 | 新增 RMC 输入卡 / 新模型变体 / 新接口 | 架构影响面、接口设计 |
| 算法实验 | 新 loss / 先验 / 训练策略对比 | 实验设置、基准对比、可复现性 |
| 缺陷修复 | WW 实现 bug、收敛异常、内存问题 | 根因证据链、影响面 |
| 性能优化 | 训练/推理/MC 循环加速 | 基线 profile、瓶颈证据 |
| 文档 | 知识库/接口规格更新 | 事实核对 |

## 目录约定

```
MLVR_develop/
  README.md                        本文件（工作流规范）
  INDEX.md                         ★ 任务总台账，一行一个任务，先看这里
  new_task.sh                      建档脚本
  _template/README.md              单任务记录模板
  YYYYMMDD_NN_<任务短名>/          ★ 一个任务一个文件夹（NN=当天工作顺序，01 起两位）
    README.md                      ★ 全过程记录（唯一主文档，含工作日志第 9 节）
    会话纪要.md                    可选：人机讨论要点（Q&A 脉络 + 共识 + 未决事项，脱敏）
    logs/                          原始报错、训练日志、失败产物（原样保存，不加工）
    changes.diff                   本次代码改动快照（人复核用）
```

> ⚠️ 原始聊天转储**不要**存进仓库（可能含口令/token）；留纪要即可，且必须脱敏。

命名示例（`NN` 为当天序号，由 `new_task.sh` 自动生成，`ls` 即见工作顺序）：
- `20260824_01_workflow-baseline/`（当天第 1 个任务）
- `20260825_04_f02-w7-neutron-only-adjoint-init-fix/`（当天第 4 个任务）

同一天多个任务靠 `NN` 序号区分先后；短名要能"看名字就知道是什么事"。

## 五步工作流

```
 ① 立项  ──► ② 设计/定位  ──►  ⛔ 停 · 你拍板  ──► ④ 实施+自验 ──► ⑤ 归档
 (Agent)      (Agent)            (人)              (Agent)        (Agent+人)
```

| 步 | 谁 | 做什么 | 产出 |
|---|---|---|---|
| ① 立项 | Agent | 你提出任务 → 建文件夹，原始材料**原样**存进 `logs/`，填写"任务定义"（目标/范围/验收标准） | 文件夹 + README 前两节 |
| ② 设计/定位 | Agent | 读代码/查知识库/跑小实验 → 给出证据（`文件:行号` / 实验数据）、影响面、**2~3 个可选方案+代价** | README"调研与设计""方案选项" |
| ⛔ 停 | **你** | 选方案、给约束（能不能动接口、能不能更新基准、算力预算…） | README"决策"（记谁决定的、为什么） |
| ④ 实施 | Agent | 改代码 → `git diff > changes.diff` → 跑验证/实验 → 贴真实输出 | 代码改动 + `changes.diff` + "验证/实验记录" |
| ⑤ 归档 | Agent→你 | 更新 INDEX 状态、同步知识库 06 条目状态；**你决定是否 commit/push** | README"结论与遗留" |

**硬规则**：第 ③ 步必须停下等你。Agent 不得在未拍板前改 `../RMC` 下的任何文件。
（只读排查、写 `MLVR_develop/` 与 `MLVR_Knowledge/` 下的记录不受此限。
`../AIMC_WWiteration/` 原型改动较宽松，但建议同样留痕。）

## 补充约定（比"只写文档"更有效，成本很低）

### 1. 改动必须落成 `changes.diff`
实施后执行：
```bash
git -C ../RMC diff > <任务文件夹>/changes.diff
# 改原型则：
git -C ../AIMC_WWiteration diff > <任务文件夹>/changes.diff
```
这样你不用翻代码仓库就能一眼看全本次改了什么。这是"人要知道代码怎么迭代"的关键抓手。

### 2. 一任务 = 一分支 = 一提交，消息里带文件夹名
```bash
git -C ../RMC checkout -b feat/mlvr-<任务短名>
git -C ../RMC commit -m "feat(mlvr): <一句话> (MLVR_develop/20260824_01_xxx)"
```
好处：**双向可查**——从 git 历史能找到档案，从档案能找到提交。
不想开分支时至少保证 commit message 里带文件夹名。

### 3. 与知识库联动
- 实现/修复的是知识库 [06_已知问题与改进建议](../MLVR_Knowledge/06_已知问题与改进建议.md)
  里的条目 → 在该条目下标注 `已修复 → MLVR_develop/<任务文件夹>`。
- 发现**新问题/新方法结论** → 归档时补写进 06 或对应专题文档，让知识库始终是最新全景。
- 改动影响架构/接口/方法 → 同步更新知识库 01~05 对应章节的"变更记录"。

### 4. 实验可复现性（涉及训练/数值实验时）

| # | 必记录项 | 位置 |
|---|---|---|
| 1 | 随机种子、`src/config.py` dataclass 配置快照 | 档案 README"实验设置" |
| 2 | 依赖版本：CUDA / PyTorch / numpy / numba / 编译器 | 档案 README"实验设置" |
| 3 | 运行命令（含 `--quick` 等 CLI 参数）、输入卡 | 档案 README 第 6 节 |
| 4 | 基准对比基线（模拟 MC / 指数 WW / 原型同变体） | 档案 README"结论" |
| 5 | 模型/权重产物（`.h5`）与生成它的配置一一对应 | 任务文件夹或知识库登记 |

### 5. 归档检查清单（⑤ 归档时逐项自检，避免人提醒才补）

| # | 检查项 | 位置 |
|---|---|---|
| 1 | 会话纪要（Q&A/共识/未决，脱敏）已补到最新一轮讨论 | 档案 `会话纪要.md` |
| 2 | README 的 状态/时间线/工作日志/结论与遗留 与新事实一致 | 档案 `README.md` |
| 3 | INDEX.md 状态已更新 | `MLVR_develop/INDEX.md` |
| 4 | 知识库 06 条目状态（已修复/🟢）与变更记录已同步 | `MLVR_Knowledge/06_…` |
| 5 | AGENT_CONTEXT「近期重要事件」已同步 | `MLVR_Knowledge/AGENT_CONTEXT.md` |
| 6 | `changes.diff` 是最新（改过 `RMC/` 或 `AIMC_WWiteration/` 才有） | 档案 `changes.diff` |
| 7 | 验证记录贴的是真实输出（哈希/diff/退出码/训练曲线），未覆盖项如实写明 | 档案 README 第 6 节 |
| 8 | 实验可复现性五项（种子/配置/依赖/命令/基准）齐全 | 档案 README |

### 6. 归档体积规范

- `logs/` 不存可再生成的产物：构建目录、二进制、RMC 运行产物、训练中间 checkpoint 等，
  需要时写重现命令而不是存文件；
- 单文件 >10MB 须先与用户确认是否必要；
- 大量同类过程文件优先**整合成脚本 + manifest**，而不是逐个上传。

## 状态词表（INDEX.md 里只用这几个）

| 状态 | 含义 |
|---|---|
| `待设计` | 已立项，尚未完成设计/定位 |
| `待决策` | 设计/根因清楚，方案已给，**等你拍板** |
| `实施中` | 已拍板，正在改 |
| `待验证` | 改完了，等本地实验 / CI / 回归结果 |
| `已完成` | 验证通过并已归档（是否 push 由你决定） |
| `已关闭` | 决定不做（须在 README 写明理由） |
