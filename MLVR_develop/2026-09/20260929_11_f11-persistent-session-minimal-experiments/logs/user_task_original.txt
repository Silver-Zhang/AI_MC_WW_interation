# 7. E0 — Startup / initialization performance decomposition

## Question

重复启动 RMC 到底浪费多少时间？

不要再只凭“数据库读取可能很慢”推断。

---

## Required timing stages

尽量分开测量：

T_process
    process creation / MPI-off startup

T_input
    input read + input checking

T_geometry
    geometry/material preparation
    如果当前无法单独拆分，可合并并明确说明

T_xs
    XSDIR / ACE / MGACE loading

T_adjoint_prepare
    adjoint derived-data preparation
    若 Forward case 不存在则记 N/A

T_transport_prepare
    source/tally/bank/transport initialization

T_transport
    actual source-history transport loop

T_tally_finalize
    reduction / Ave / RE / normalization

T_output
    text/file output

T_total

当前 RMC timer 若不能提供这些边界：

优先采用最小、局部、test-only timing instrumentation。

如果需要修改生产源码才能准确测量，先停止并提出 instrumentation patch。

---

## Cases

至少测：

A. Forward
B. Adjoint

每种建议：

- warm-up 1 次
- 正式 5 次以上
- 相同 population
- 记录 mean / std
- 明确文件系统 cache 是 warm 还是 cold

不需要为了 E0 跑大粒子数。

目标是比较：

startup+init

vs

transport

比例。

---

## E0 output

报告：

T_total =
T_startup/init
+
T_transport
+
T_finalize/output

重点给：

startup/init fraction

不要根据单次 noisy timing 下结论。

# 8. E1 — Same-process Forward → Forward

## Question

同一模型只初始化一次后，连续执行两个独立 Forward calculations 是否可行？

---

## Fresh-process oracle

准备两个独立 fresh-process runs：

Fresh F1
Fresh F2

使用明确 seed namespace。

例如：

F1 seed = S1
F2 seed = S2

---

## Same-process target

目标逻辑：

Initialize model once

Run Forward:
    population=N1
    seed=S1

reset calculation state

Run Forward:
    population=N2
    seed=S2

---

## Must inspect/reset

至少覆盖：

- p_nFinishCalculate
- completed-history counters
- fixed source counters
- particle banks
- descendant banks
- total starting weight
- source statistics
- RNG position/cache
- tally score
- Sum1/Sum2
- Ave/RE
- timing state
- diagnostics
- output state

---

## Pass conditions

第二轮必须：

1. 实际执行 N2 histories；
2. 无第一轮 bank residue；
3. tally statistics 不含第一轮；
4. normalization 正确；
5. 与 Fresh F2 在冻结比较标准下等价；
6. 第一轮结果与 Fresh F1 等价。

必须证明：

Run2 is independent from Run1

而不是仅得到一个“看起来合理”的 Ave。

---

# 9. E2 — Forward → Adjoint → Forward

## Question

这是决定 persistent RMC 是否现实的核心实验。

---

## Oracle

分别做 fresh process：

Fresh Forward 1
Fresh Adjoint
Fresh Forward 2

---

## Same-process sequence

Initialize frozen model once

Forward(S1)
    ↓
switch / rebuild required state
    ↓
Adjoint(S2)
    ↓
switch / rebuild required state
    ↓
Forward(S3)

---

## Must observe

运行前后记录：

- FixedSource adjoint flag
- AceData adjoint state
- Particle role
- MaxAdjointEnergy physical value
- internal MG group representation
- adjoint XS arrays
- fission adjoint arrays
- relevant derived caches
- material / nuclide object identity
- source identity
- tally state
- WW identity

特别检查之前源码审查发现的：

1. flag only set true path
2. MaxAdjointEnergy MeV → group index mutation
3. TreatAdjointMaterial += accumulation
4. stale particle XS/cache

---

## Pass condition

每个阶段都必须与对应 fresh-process oracle 一致。

尤其：

第三个 Forward

必须证明没有残留 Adjoint 状态。

如果失败：

不要立即修复。

首先定位：

- 哪个 state 不一致
- 从哪一步开始偏离
- 应属于 CLEAR / REBUILD / immutable-base redesign 哪一类

输出最小 blocker。

# 10. E3 — WW hot update

## Question

固定：

mesh
energy groups
WW parameters

只改变：

WW lower bounds

下一轮是否能正确使用新 WW？

---

## Design

构造两个明显不同的 WW：

WW1
WW2

必须让选定几个 mesh×group bin 的 lower bound 差异足够明显。

不要通过最终 FOM 判断是否更新成功。

需要直接观察：

particle state
→ selected mesh/group
→ selected lower bound

---

## Compare

Fresh process WW1

Fresh process WW2

same-process:

WW1
→ update
→ WW2

第二轮必须与 Fresh WW2 的查窗行为一致。

---

## Must inspect

- lower bounds
- survival bounds
- upper bounds
- WW parameters
- mesh identity
- energy-grid identity
- derived arrays/cache
- particle-type tables

如果 survival/upper 由 lower 派生：

必须确认更新后重新计算。

---

## Pass condition

不仅数组看起来变了，还必须证明：

运输实际读取的是 WW2。

# 11. E4 — Tally reset + in-memory Field extraction

## Question A

能否保留：

mesh/tally definition

只清：

per-run statistics

然后执行下一轮？

---

## Run design

使用两轮故意明显不同的 source / population / seed，使两个 field pattern 可区分。

Run1
→ snapshot
→ reset
→ Run2
→ snapshot

---

## Check reset

至少检查：

- per-history score
- touched/index sets
- Sum1
- Sum2
- Ave
- RE
- statistics tester state
- tally registry size

第二轮不得保留 Run1 数据。

---

## Question B

定位归一化完成后的内存：

value[i,g]
RE[i,g]

并验证其与 `.Tally` 文本输出一致。

不要实现正式 F10 Adapter/API。

只证明：

结构化数组在什么时刻可读取。

---

## Also extract

尝试从 MGACE 内存结构构造：

physical G+1 energy boundaries

检查：

- G+1 length
- MeV
- strictly increasing
- physical ascending
- highest upper bound
- mapping to Tally Group rows

这是 F10 后续实现的重要证据。
